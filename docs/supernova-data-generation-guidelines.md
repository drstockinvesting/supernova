# Supernova: Synthetic Data Generation Approach

## How This Differs From the Data Structures Doc

`supernova-data-structures.md` defines the **shape** of the data — the fields, records, and relationships. This document defines the **logic** used to fill that shape with synthetic values. It's meant to guide a Claude Code prompt (or set of prompts) that programmatically generates the synthetic student dataset — not to define the schema itself.

---

## Core Principle: Patterns, Not Randomness

Synthetic data should not be generated by independently randomizing each field for each student. Independently randomized fields produce statistically "valid" but narratively incoherent students — a student with perfect attendance and no mastery, or a student with a discipline record from a school they never attended. That kind of noise:

- Undermines the dashboards' correlation and narrative features, which depend on real relationships existing in the data to surface
- Produces stories that don't read as plausible to a teacher, parent, or board member reviewing the prototype
- Fails the actual test of the system: does the data *tell a believable story*?

Instead, data should be generated **archetype-first**: each synthetic student is seeded from a recognizable, real-world education pattern, and every data stream for that student (mastery, attendance, behavior, health, family engagement, special services, prior achievement) is generated to be internally consistent with that pattern.

---

## What "Grounded in Typical Flows" Means

Before generating a student's data, the underlying pattern should answer, in plain language a non-technical person would recognize:

- What is going on with this student, generally?
- How does that show up in each data stream?
- Would a teacher who's seen a lot of students say "yeah, I've had a kid like this"?

If the answer to that last question is no, the archetype needs rethinking — the point is recognizability, not statistical novelty.

---

## Archetype-Based Generation

Each archetype is a short case-study description that seeds one student's full record. The archetype determines the *direction and shape* of the data; individual values (exact dates, exact scores, exact names) are still varied per student so the dataset doesn't feel duplicated.

### Illustrative Archetypes (Starting Set)

**1. Steady High Achiever**
Consistent attendance, consistent mastery growth across subjects, minimal behavioral incidents, engaged family. Nothing dramatic — the point is to have a believable baseline "everything is working" student in the dataset.

**2. Chronic Absenteeism Recovery**
A student who missed significant instructional time earlier in the year (attendance rate well below 90%), showing corresponding mastery gaps concentrated in the units taught during the absences — then attendance improves in recent months, with early signs of mastery catching up. This is the flagship example for the attendance-to-mastery correlation narrative described in the UI/UX design.

**3. IEP Student on Track**
A student with an active IEP and specific accommodations, whose mastery evidence is generated consistently with their IEP goals rather than as a separate, disconnected data stream. Progress is steady but slower on certain standards, with evidence explicitly linked to IEP goal progress.

**4. Behavioral Disruption Concentrated in One Class**
A student with no attendance or health flags, generally fine mastery in most subjects, but a cluster of behavioral incidents during a specific unit or class period — with a visible mastery dip in that subject specifically, not across the board. This tests whether the system correctly isolates correlation rather than assuming a struggling student struggles everywhere.

**5. Late Start, Strong Finish**
Weak mastery evidence and low engagement early in the year, followed by a genuine turnaround — rising attendance, increasing evidence strength, mastery status flipping from "not mastered" to "mastered" on multiple standards in the back half of the year. Useful for testing trend/direction indicators, not just current-state snapshots.

**6. Family Engagement Gap**
Solid attendance and average mastery, but minimal family contact-event history (low conference attendance, low response rate to outreach) — testing whether the system surfaces this as its own signal rather than assuming disengaged families always correlate with struggling students.

**7. Transfer Student, Incomplete History**
Enrolled mid-year or mid-elementary-career from another district, with a genuinely sparse or partial `PriorAchievementRecord` and longitudinal profile — data quality flags should reflect the gap honestly rather than the generator inventing a full fake history to fill it in.

This starting set is intentionally small and should be expanded only with the same "would a teacher recognize this" test — not by adding statistically distinct but narratively empty variations.

---

## Distribution Across the Synthetic Population

Across the full synthetic roster (K–12, ~20 students per class), archetypes should be distributed the way real classrooms actually look, not evenly:

- Most students should land closer to "typical" / "steady" patterns
- Extreme patterns (severe chronic absenteeism, dramatic turnarounds) should be the minority, the way they are in a real classroom
- A single class shouldn't be populated entirely with dramatic archetypes just because they're more interesting to look at — realism means most of the room is unremarkable, with a handful of standout stories

---

## Guidance for the Claude Code Generation Prompt

When this document is handed to Claude Code for actual data generation, the prompt should:

1. Assign each synthetic student an archetype (or a light blend of two) before generating any field-level data
2. Generate each of the seven data streams for that student *from* the archetype description, so attendance, behavior, mastery, and the other streams are mutually consistent
3. Vary specifics (exact dates, exact evidence counts, exact scores within a plausible range) so students sharing an archetype don't look identical
4. Preserve the archetype's internal logic over strict randomness — e.g., a "chronic absenteeism recovery" student's absence dates should cluster in identifiable ways, not scatter uniformly across the year
5. Keep the overall population distribution weighted toward typical/steady patterns, per the section above

---

## What This Document Is Not

- It is not the data schema — see `supernova-data-structures.md` for exact fields and record types
- It is not a full list of every archetype the final dataset will use — it's a starting set meant to establish the *method*, which can be extended with additional archetypes later using the same "recognizable to a teacher" standard
